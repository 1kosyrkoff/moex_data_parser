# Облигационные данные: сервисная обвязка

Исходные `moex_bonds.py` и `moex_cls.py` используются без изменений.
Их прежние импорты, результаты и демонстрационные запуски продолжают работать.
Описание функций и методики: [spec-moex-bonds.md](spec-moex-bonds.md).

## Архитектура

```text
Docker Compose
  worker: планировщик → новый процесс run_pipeline для каждого прогона
                             ↓
             существующие функции MOEX и расчёты коллеги
                             ↓
                     storage → PostgreSQL
                                      ↓
                          api (роль только для чтения)
                                      ↓
                          будущий/существующий интерфейс
```

Три постоянных контейнера: `postgres`, `worker`, `api`. Отдельные брокеры задач,
Redis, Celery и новые финансовые формулы не используются. Интерфейс в этой ветке
не создаётся: для его подключения предоставлен API.

## Порядок обновления

1. Получить текущий список MOEX через `market_snapshot()`.
2. Оставить непустые уникальные ISIN, сохранив исходный порядок. Все строки
   справочника для каждого выбранного ISIN сохраняются в `instruments`.
3. Разбить список на пачки (по умолчанию 25).
4. Для каждой бумаги пачки вызвать `get_bond_card()` и одной транзакцией
   сохранить карточку и вложенный `schedule` в разные таблицы. Повторного вызова
   `get_coupon_schedule()` нет; исходный словарь не изменяется.
5. Вызвать `get_bond_yields(details=True)` и `get_issuer_sector()` для всей пачки,
   сохранить результаты по ISIN. Сами функции обрабатывают список последовательно.
6. Получить свечи через `get_candles()` и сохранить. На первом прогоне — заданный
   период, затем — новые даты с перекрытием последних семи дней для уточнений.
7. Записать итог прогона и завершить процесс.

Дата оценки фиксируется один раз на весь прогон, по умолчанию сегодня в Москве.
Источник цены (`close`), lookback и допущения по купонам соответствуют исходным
функциям. Параметры сохраняются в журнале. Режим торгов берётся из исходного
справочника: автоматической подмены `SPOB` на `TQOB` нет. Пустые котировки
и объясняющий `STATUS` сохраняются как результат. `--candle-board` позволяет
явно выбрать другой режим только для свечей; расчёт доходностей не меняется.

Каждый прогон — новый интерпретатор, поэтому кеш коллеги не застывает между
обновлениями. PostgreSQL advisory lock не допускает двух одновременных прогонов.
Незавершённый предыдущий прогон после освобождения блокировки отмечается
`interrupted`. Новый запуск снова проходит выбранный список; автоматического
продолжения с середины нет. Уже записанные снимки остаются доступны.

Первый прогон планировщика начинается сразу. Следующий — через
`BOND_UPDATE_INTERVAL` секунд после завершения, а не в фиксированное время суток.
`BOND_RUN_TIMEOUT` ограничивает длительность дочернего процесса. Остановка worker
передаёт сигнал дочернему процессу.

## PostgreSQL

| Таблица | Содержание |
|---|---|
| `bond.runs` | Параметры, SHA-256 исходных модулей, версия сборки, статусы, счётчики и ошибки |
| `bond.instruments` | Результат справочника, сгруппированный по ISIN |
| `bond.cards` | Все разделы карточки, кроме `schedule` |
| `bond.schedules` | Таблица `card['schedule']` |
| `bond.yields` | Собственные доходности и диагностика коллеги |
| `bond.sectors` | Сектор, источник определения и STATUS |
| `bond.candles` | Свечи по ISIN, режиму торгов и времени |

Снимки связаны через `(run_id, isin)`. В `payload` JSONB хранятся исходные названия
колонок, строки, порядок, индекс и описания pandas-типов. Даты сериализуются в ISO,
`NaN`/`NaT`/`pd.NA` и нечисловые бесконечности — в JSON `null`; денежные суммы и
доходности не округляются и не пересчитываются. JSONB — транспортное представление
результата, не pickle Python-объекта. Свечи хранятся построчно, включая прежние версии.

Повторная запись одного `(run_id, isin)` обновляет только этот снимок. Новый прогон
добавляет историю. Старые выпуски и данные не удаляются при исчезновении из списка.
Срок хранения пока не ограничен; очистка истории не запускается автоматически.

`latest_*` — SQL-представления последних пригодных результатов. Технические ошибки
в `STATUS` сохраняются с `usable=false` и не скрывают предыдущие данные. Отсутствие
сектора, цены, будущей суммы купона или YTM бессрочной бумаги само по себе не считается
техническим сбоем. Если функция выбросила исключение, причина записывается в `runs`;
остальные функции/бумаги продолжают обрабатываться.

`bond.coupon_events` разворачивает последнее расписание в общий SQL-календарь.
Необъявленный купон остаётся NULL. Выкуп по оферте не прибавляется к `total_amount`.

## Локальный запуск / будущая ВМ

Нужны Docker Engine и Compose v2. Команды ниже — инструкция, не автоматическая
выкладка. Из каталога репозитория:

```bash
cp .env.example .env
```

Заполнить четыре разных пароля/токена; например, каждый генерировать командой
`openssl rand -hex 32`. `.env` не включается в Git и образ. Затем:

```bash
export SOURCE_REVISION=$(git rev-parse HEAD)
docker compose config --quiet
docker compose up -d --build
docker compose logs -f worker
```

По умолчанию обрабатываются **только пять выпусков за 30 дней истории** — настройки
первой проверки. Для текущего рынка целиком установить в `.env`:

```dotenv
BOND_RUN_ARGS=--history-days 365
```

После изменения настроек: `docker compose up -d worker`. Для ручного запуска
одного прохода при работающей БД (блокировка защищает от пересечения с worker):

```bash
docker compose run --rm worker python -m bond_service.run_pipeline \
  --isins RU000A106E90 --date 2026-10-15 --history-days 30 --candle-board TQOB
```

`--history-days 0` выключает свечи. `--limit N` ограничивает число выпусков.
Все дополнительные параметры: `python -m bond_service.run_pipeline --help`.
Покрытие — текущий справочник MOEX, не все внебиржевые и исторические выпуски.

Схема и роли создаются `deploy/schema.sql` при **первой инициализации пустого тома**.
Для существующего тома изменения `.env` не меняют пароли ролей автоматически.
Будущие изменения структуры требуют явного применения миграции; запуск worker
самостоятельно не меняет схему.

API опубликован только на `127.0.0.1:8793`. PostgreSQL наружу не публикуется.
Для внешнего доступа позже потребуется HTTPS через reverse proxy выбранной ВМ.
Данные PostgreSQL находятся в постоянном томе `bond-data`; `docker compose down`
сохраняет их. Резервная копия:

```bash
docker compose exec -T postgres pg_dump -U bond_admin -d bonds -Fc > bonds.dump
```

## API

`GET /health` проверяет доступность БД. Для остальных запросов нужен заголовок
`Authorization: Bearer <BOND_API_TOKEN>`.

| Запрос | Ответ |
|---|---|
| `GET /bonds?limit=100&offset=0` | Последний справочник выпусков, постранично |
| `GET /bonds/{isin}` | Последние пригодные результаты каждого этапа |
| `GET /bonds/{isin}?run_id=<uuid>` | Снимки конкретного прогона, включая технические статусы |
| `GET /bonds/{isin}/candles?start=2026-01-01&end=2026-10-15&board=TQOB` | История свечей |
| `GET /calendar?start=2026-10-01&end=2026-12-31&limit=1000&offset=0` | Общий календарь событий |
| `GET /runs?limit=20` | Итоги и ошибки последних прогонов |

Каждый результат содержит свой `run_id` и `collected_at`: после частичного сбоя
разные этапы могут показывать данные разных прогонов, что видно явно. Свечи по
умолчанию ограничены 1000 строками; можно задать `limit` до 10000 и сузить даты.
API работает под отдельной SQL-ролью `bond_reader` без прав записи, не импортирует
парсер и не делает запросов к MOEX. Запуск API под ролью с INSERT запрещён.

## Проверки без внешних запросов

```bash
python -m pip install -r requirements-test.txt
python -m pytest tests/test_bond_service.py -q
```

Без PostgreSQL выполняются проверки сериализации и классификации статусов.
Для интеграционных тестов подготовить **отдельную тестовую** PostgreSQL со схемой
из `deploy/schema.sql`, ролями `bond_writer` / `bond_reader` и базой, имя которой
оканчивается на `_test`. Тесты очищают данные только этой тестовой базы.
Установить `TEST_PGPORT`, `TEST_PGDATABASE`, `TEST_WRITER_PASSWORD`,
`TEST_READER_PASSWORD`; сервер должен быть доступен на `127.0.0.1`.
Все HTTP-запросы в тестах заблокированы. Проверяются round-trip значений, календарь,
атомарность, повторная запись, история, частичный сбой, блокировка, права и API.

Зависимости образа зафиксированы в `requirements-service.lock`; исходные ограничения
для их осознанного обновления — `requirements-service.txt`.
